# Approved chapter presentation — mandatory execution contract

Read this file and `presentation-profile.json` in full in the existing Chapter Writing worker. This is a reference inside that worker, not another skill or node. This contract resolves legacy template conflicts; the bundled registry skill texts remain unchanged.

## Stable presentation profile

Use `personal-agents-approved-v1` for every newly generated chapter and explicit style repair unless the author expressly selects a different profile. The profile captures the observed corrected Personal Agents document, its exact ID and revision; it does not depend on another account having access to that private document. Never copy that chapter's content or evidence. Retain the current chapter's approved structural order, meaning and evidence.

- Render main sections as native HEADING_1 with main numbering `1.`, `2.`, etc.; use a small, meaningful functional icon at important main headings, as in the reference. Plan the icons explicitly before writing. "Sparingly" is not permission to omit all icons in a full chapter.
- Render subsection titles as native HEADING_2 without hierarchical numbers. `3.1` and `3.2` remain internal mapping locators in Notes/coverage, not reader headings. Preserve each title's words/order. Treat `[TECH]` / `[WOW MOMENT]` as internal commitments: retain their substantive explanation/fixed punchline, record their mapping, and do not print internal tags or workflow labels in the reader chapter.
- Select important existing opening claims or comparison phrases for native bold. Identify concrete paragraph openings while developing the argument; preserve useful middle/end emphasis. Zero opening emphasis does not satisfy the approved full-chapter profile. Do not add preview-label sentences, bold every paragraph or use a numeric aesthetic quota.
- Find genuinely parallel explanations, comparisons or reader action questions. Plan explanatory native bullets where they help, with meaningful bold lead-ins and complete explanations. Do not satisfy the check with a token fragment list at the end. Review opportunities across the chapter; ordinary prose stays prose. Maximum two lists per section unless the author overrides.
- Integrate concise italic source/study attribution and plain parenthetical evidence citations. Do not hyperlink reader citation text by default. Keep every exact source URL and source-to-claim/section locator in the Handoff citation table, with clickable links there. This changes presentation only, not evidence availability or citation meaning. No evidence colour/highlight and no removal of sources.
- Match the observed reference: Georgia title 26 pt (TITLE), main HEADING_1 17 pt, subsection HEADING_2 13 pt, black text with no crimson heading overlay; body Georgia, 115% line spacing and 7 pt below. Use 12 pt as explicit production body default because the baseline body size is inherited and absent from native readback. Title spacing is 16 pt above/below; main headings 22 pt above/10 below; subsections 14 pt above/7 below. Preserve selective inline emphasis and bold fixed punchlines. A title is distinct from main sections. No new images here; Visual Placement still places approved images only.

## Plan, apply, prove

Before writing, make a `presentation_plan` in Notes following the schema consumed by `scripts/validate_chapter_presentation.py`. Record the profile/baseline identity, complete expected reader heading sequence/styles, chosen heading icons, specific existing paragraph opening prefixes to bold, explanatory list items and bold lead-ins, citation anchors and their exact source URLs/locators. Plan by argument opportunities, not quotas. Do not silently drop a feature; an exceptional omission needs an explicit author instruction, not a worker preference.

After writing and after every native format conversion/repair, read back the actual Doc. Bind the plan to its real Doc ID and final revision. Run the native presentation validator on the complete Google Docs JSON and plan, not a worker-generated count summary. Repair failures in the same unpublished Doc and rerun. Save stable plan locators in Notes/Handoff. After the last write, bind the actual revision in a separate exported execution envelope and durable execution evidence; do not insert the final revision into the same Doc and thereby invalidate it. Worker-only tests must pass this same presentation check before returning success; stopping before the evaluator does not waive it.

A count of bold runs or bullets is not proof. Verify planned opening bold starts at the actual paragraph beginning, icons are in the planned headings, bullets are native and explanatory, reader subsection numbering is absent, and source URLs remain in Handoff. Record the exact locators/results, not generic "PASS".

The clean evaluator independently checks whether these choices serve the argument and match the approved sample, and reruns the native check on the current revision. It adds `presentation` to the execution receipt: profile/baseline provenance, Artifact A revision, validator outcome and locatable evidence. Missing, failed or stale evidence blocks handoff regardless of weighted score. The deterministic validator proves placement/preservation, not literary quality.

Rendering repairs do not create an extra workflow node. Storytelling -> integrated writing/formatting/internal humanizer -> story-integrity -> native presentation verification remains one Chapter Writing worker. Visual Placement must preserve that presentation unchanged.
